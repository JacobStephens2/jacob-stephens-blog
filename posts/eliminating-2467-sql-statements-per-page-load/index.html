Eliminating 2,467 SQL Statements per Page Load

The page that printed before every trip took 5-7 seconds to load and fired roughly 2,650 SQL statements per render. When I was done it fired 183. The interesting part isn't the number - it's that the work split cleanly into three phases that I think generalize to almost any "this page got slow" problem: measure, fix, prevent. A junior engineer stops after the fix. A senior one doesn't.

Measure

I didn't guess. I captured an xdebug cachegrind profile of a real request and read it top-down. The shape was immediately familiar: an N+1 explosion. The page renders a group reservation - up to ~50 passengers - and for each passenger the object constructors for the booking, the price statement, and the payment schedule each ran their own helper queries. Fifty passengers × several constructors × several helper queries each is how you get to ~2,650 statements without anyone writing a single obviously-bad query. It was also opening 118 fresh database connections per request, because one code path reached for a new connection instead of the shared handle.

The lesson I keep relearning: N+1 problems are invisible in the code and obvious in the profile. You will not find them by reading; you find them by measuring.

Fix

Three moves, in order of payoff:

  1. One connection. Route the stray new connection through the shared handle the page already had open. 118 connections per request became one.
  2. Batch the per-row work. Make the heavy constructor skippable for child-row loads, then hydrate all ~50 passengers with a single batched IN (...) query instead of 50 sets of per-row helper calls.
  3. Prefetch once. Add a small prefetch layer for the price-statement data: a handful of static caches and batched lookups warmed once before the per-passenger loop, with per-instance fallbacks so callers outside this page kept working unchanged.

The constraint I held the whole time: byte-identical output. At the end of every round I diffed the rendered HTML against the original and required it to match exactly. A performance change that alters output isn't a performance change, it's a feature change with a performance side effect - and it's how you quietly break a document people rely on.

Prevent

Here's the phase that matters most and gets skipped most. One of the slow queries used a leading-wildcard LIKE '%...%' against a history table - the kind of predicate that can never use an index and gets slower as the table grows. Speeding up the surrounding code would have left a regression waiting to happen. So I added a dedicated column and a composite index that captured the thing the LIKE was actually testing for, and rewrote the query against it. The rows examined per lookup dropped from ~4,165 to 1.

That's the difference between "I made it fast today" and "it stays fast as the data grows." A schema/index change is the only one of the three phases that prevents the problem from coming back.

The result, and the scaling check

Production dropped from 5-7 seconds to about one. Statements per request went from ~2,650 to 183 - about a 93% reduction - and the connection storm collapsed into the single handle the page already held. HTML byte-identical throughout.

Then I did the thing that separates "works on my test case" from "works": I re-ran it against the worst real group in the system - 244 sub-reservations, several times larger than normal. There the same code took the page from ~10 seconds to ~3, and from ~11,800 statements to ~2,400, still byte-identical. The wins scaled to the outlier, which is the only proof that matters.

Takeaways

  • Profile before you touch anything. The fix is usually boring once you can see the shape; finding the shape is the work.
  • Batch and prefetch instead of looping. Most N+1s die to one IN (...) query and a warmed cache.
  • Hold output constant. Byte-identical diffs turn "trust me" into proof.
  • Finish with prevention. A column and an index are what keep the win from eroding. If you stopped at the fix, you're not done.
